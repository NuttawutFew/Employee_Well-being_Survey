# ระบบประเมินสุขภาพใจ — Design Specification

- วันที่: 2026-09-03
- สถานะ: พร้อมให้ผู้ใช้ตรวจทาน
- เอกสารประกอบ: `docs/domain-model.md`, `docs/glossary.md`, `docs/adr/`

## 1. เป้าหมาย

สร้างระบบภายในองค์กรสำหรับให้พนักงานประเมินสุขภาพใจด้วยตนเองหนึ่งครั้งตลอดอายุระบบ โดยทำแบบประเมิน 5 ชุดตามลำดับตายตัว เมื่อส่งครบแล้วพนักงานเห็นผลของตนเอง และ Admin/HR เห็นผลรายบุคคลกับสถิติรวมผ่านเว็บแยก

ระบบเป็นเครื่องมือคัดกรอง ไม่ใช่การวินิจฉัย ไม่มีเจ้าหน้าที่เฝ้าระวังแบบเรียลไทม์ และไม่ส่งการแจ้งเตือนอัตโนมัติเมื่อพบความเสี่ยง

## 2. ผู้ใช้และเว็บแอปพลิเคชัน

### 2.1 Employee Assessment Web

พนักงานทุกคน รวมถึงบุคลากร HR ในฐานะพนักงาน เข้าใช้ผ่าน OnePlatform ระบบรับ `shareToken` ไปแลกโปรไฟล์และสร้าง session โดยใช้รหัสพนักงานที่ไม่ซ้ำและคงที่เป็น identity

เว็บรองรับมือถือ แท็บเล็ต และ PC อย่างเต็มรูปแบบ โดยออกแบบ mobile-first

### 2.2 Admin Web

เว็บแยกสำหรับ Admin/HR ที่ได้รับสิทธิ์ ใช้บัญชีและรหัสผ่านภายในระบบ ไม่ใช้ OnePlatform และไม่บังคับ MFA บัญชีถูกสร้าง ปิดใช้ และรีเซ็ตผ่านเครื่องมือหลังบ้านโดยนักพัฒนาที่ได้รับสิทธิ์ ไม่มีหน้าจัดการบัญชี

Admin Web เน้น desktop แต่ต้อง responsive และใช้งานได้บนแท็บเล็ตกับมือถือ

## 3. หน้าชี้แจงก่อนเริ่ม

หลังยืนยันตัวตนสำเร็จและก่อนสร้าง Draft ระบบแสดงคำชี้แจงซึ่งครอบคลุม:

- วัตถุประสงค์และขอบเขตการคัดกรอง
- แบบประเมินทั้ง 5 ชุด
- ข้อมูลที่เก็บและการผูกผลกับตัวตน
- การที่ Admin/HR เข้าถึงผลรายบุคคลและ export ได้
- อายุข้อมูล 1 ปีและการทำให้ไม่ระบุตัวตนหลังครบอายุ พร้อมเก็บ Audit Log 2 ปี
- ข้อจำกัดว่าไม่ใช่การวินิจฉัยและไม่มีเจ้าหน้าที่ติดตามแบบเรียลไทม์
- ช่องทางติดต่อผู้ดูแลระบบหรือผู้ควบคุมข้อมูล

ปุ่มหลักใช้ข้อความ “รับทราบและเริ่มทำแบบประเมิน” เมื่อกดแล้วจึงเก็บ notice version, เวลา และรหัสพนักงาน พร้อมสร้าง Draft หากยังไม่กด ระบบไม่สร้าง Draft หรือบันทึกคำตอบ

ข้อความนี้เป็นการรับทราบ ไม่ถูกนิยามแทนฐานกฎหมายหรือความยินยอม และต้องผ่านฝ่ายกฎหมาย/PDPA ก่อน production

## 4. แบบประเมินและลำดับ

ไฟล์ต้นฉบับใน workspace เป็นแหล่งอ้างอิงด้านคำถาม ตัวเลือก คะแนน และเกณฑ์ ภาพหน้าจอทั้งหมดเป็นตัวอย่าง UX/UI เท่านั้น

ลำดับและจำนวนข้อ:

1. Burnout — 22 ข้อ
2. Stress — 20 ข้อ คะแนนเต็ม 60 ไม่ใช้ ST-5
3. Resilience/RQ — 20 ข้อ
4. Depression/9Q — 9 ข้อ
5. Suicide Risk/2Q Plus — 3 ข้อ

มีหน้าคำถาม 5 หน้า หนึ่งหน้าต่อหนึ่งแบบประเมิน แต่ละหน้าแสดงคำถามทั้งหมดของชุดนั้น ทุกข้อเป็น required เมื่อกดไปหน้าถัดไป หากตอบไม่ครบ ระบบแสดง error ใกล้คำถามและ error summary แล้วเลื่อน/focus ไปยังข้อแรกที่ยังว่างโดยไม่ล้างคำตอบอื่น

ผู้ใช้ย้อนกลับและแก้ไขคำตอบทุกหน้าได้ตราบใดที่เป็น Draft ระบบบันทึกคำตอบอัตโนมัติและกลับมาทำต่อได้หลังปิดเว็บหรือ session หมดอายุ

## 5. Lifecycle และข้อจำกัดหนึ่งครั้ง

สถานะหลักคือ:

`Notice → Draft → Submitted`

- มี Draft ที่ active ได้สูงสุดหนึ่งรายการต่อพนักงาน
- มี Submitted ที่ยังไม่ Cancelled ได้สูงสุดหนึ่งรายการต่อพนักงานตลอดอายุระบบ
- ไม่มี Campaign หรือรอบประเมินรายปี
- พนักงานล้าง Draft และเริ่มใหม่ได้ก่อนส่ง
- หลังตอบหน้า 5 ครบ ระบบแสดง confirmation dialog พร้อม “กลับไปตรวจสอบ” และ “ยืนยันส่งแบบประเมิน”
- Submit ต้อง idempotent และทำภายใน transaction เดียว: ตรวจความครบถ้วน ล็อกคำตอบ คำนวณผล และสร้าง employee snapshot
- Submitted แก้ไขไม่ได้

Admin Reset เปลี่ยน Submitted เดิมเป็น Cancelled บันทึกผู้ดำเนินการ เวลา และเหตุผล แล้วเปิดสิทธิ์ให้พนักงานสร้าง Draft ใหม่ ผลเดิมยังคง immutable เพื่อ audit แต่ไม่แสดงเป็นผลปัจจุบันและไม่รวม dashboard

## 6. Scoring และ Interpretation

กฎคะแนนเป็น deterministic, versioned และไม่ขึ้นกับ locale หรือ UI ระบบไม่รวมคะแนนต่างเครื่องมือเป็นคะแนนสุขภาพใจเดียว

### 6.1 Burnout

แสดงผล 3 มิติ:

- ความอ่อนล้าทางอารมณ์: 0–16 ต่ำ, 17–26 ปานกลาง, ตั้งแต่ 27 สูง
- การลดความเป็นบุคคล: 0–6 ต่ำ, 7–12 ปานกลาง, ตั้งแต่ 13 สูง
- ความสำเร็จส่วนบุคคล: 0–31 สูง/หมดไฟต่ำ, 32–38 ปานกลาง, 39–48 ต่ำ/หมดไฟสูง

ข้อทางลบให้คะแนนความถี่ 0–6 ข้อทางบวก 4, 7, 9, 12, 17, 18, 19 และ 21 ให้คะแนนย้อนกลับ 6–0 ตาม ADR-0015

### 6.2 Stress

ใช้ 20 ข้อ ตัวเลือก 0–3 และแปลผล:

- 0–5
- 6–17
- 18–25
- 26–29
- 30–60

ชื่อระดับและคำอธิบายใช้ตามเอกสารต้นฉบับ

### 6.3 Resilience/RQ

กลุ่มคะแนนทางบวกใช้ข้อ 2, 3, 4, 6, 7, 8, 9, 10, 11, 12, 13, 17, 18, 19, 20 และกลุ่มย้อนกลับใช้ข้อ 1, 5, 14, 15, 16

เกณฑ์รายมิติ:

- ความทนต่อแรงกดดัน: `<27`, `27–34`, `>34`
- ความหวังและกำลังใจ: `<14`, `14–19`, `>19`
- การต่อสู้เอาชนะอุปสรรค: `<13`, `13–18`, `>18`
- คะแนนรวม: `<55`, `55–66`, `>66`

ค่าดังกล่าวรวมการแก้ข้อ 6 ที่ซ้ำเป็นข้อ 9 และแก้ขอบเขตคะแนนรวมตาม ADR-0014

### 6.4 Depression/9Q

- น้อยมาก: `<7`
- น้อย: 7–12
- ปานกลาง: 13–18
- รุนแรง: ตั้งแต่ 19

ข้อ 9 เป็นส่วนหนึ่งของคะแนนรวม 9Q เท่านั้น ไม่สร้างสถานะความเสี่ยงฆ่าตัวตายของระบบ

### 6.5 Suicide Risk/2Q Plus

เป็นหนึ่งแบบประเมินที่มีผลสองด้าน:

- ความเสี่ยงซึมเศร้า: พบเมื่อข้อ 1 หรือ 2 ตอบ “มี”
- ความเสี่ยงฆ่าตัวตาย: พบเมื่อข้อ 3 ตอบ “มี” เท่านั้น

ข้อความผลบวกใช้ “พบความเสี่ยงฆ่าตัวตาย” ไม่เติมระดับสูง/กลาง/ต่ำ

### 6.6 สถานะภาพรวม

แสดง “ควรได้รับการดูแลสุขภาพใจเพิ่มเติม” เมื่อเข้าเกณฑ์อย่างน้อยหนึ่งด้าน:

- Burnout มีมิติระดับปานกลางหรือสูง
- Stress ตั้งแต่ 18
- RQ มีมิติใดต่ำกว่าเกณฑ์ปกติ
- 9Q ตั้งแต่ 7
- 2Q Plus ตอบ “มี” อย่างน้อยหนึ่งข้อ

หากข้อ 3 ของ 2Q Plus ตอบ “มี” สถานะ “พบความเสี่ยงฆ่าตัวตาย” มีลำดับการสื่อสารสูงสุด แต่ระบบไม่ส่ง notification และเวอร์ชันแรกยังไม่แสดงช่องทางติดต่อ การตัดสินใจนี้ต้องถูกทบทวนโดยผู้เชี่ยวชาญและเจ้าของระบบก่อน production

## 7. หน้าผลพนักงาน

หน้าสรุป mobile-first แสดง:

- สถานะภาพรวม
- ข้อความว่าเป็นการคัดกรอง ไม่ใช่การวินิจฉัย
- การ์ดรายแบบครบ 5 ชุด
- ชื่อ คะแนน ระดับ คำอธิบาย และคำแนะนำของแต่ละผล
- ผล Burnout และ RQ แยกรายมิติ
- ผล 2Q Plus แยกความเสี่ยงซึมเศร้ากับความเสี่ยงฆ่าตัวตาย

เนื้อหาคำแนะนำต้องมี assessment/level, source, version, effective date และ approver ร่างเริ่มต้นอยู่ใน `docs/content/recommendations-draft.md` และห้ามนำขึ้น production ก่อนผู้เชี่ยวชาญอนุมัติ

## 8. Employee Snapshot

ตอน Submit ระบบเก็บ snapshot จาก OnePlatform ได้แก่:

- รหัสพนักงาน
- ชื่อและนามสกุล
- เพศและอายุ
- เบอร์โทร
- บริษัท แผนก และตำแหน่ง
- พื้นที่ปฏิบัติงาน
- ข้อมูลที่ใช้คำนวณอายุงาน

รายงานย้อนหลังใช้ snapshot ณ วันส่ง ไม่ดึงข้อมูลล่าสุดมาเปลี่ยนความหมายย้อนหลัง

## 9. Admin Web

### 9.1 ตารางรายบุคคล

แสดงวันที่ employee snapshot คะแนน และระดับผลของแต่ละแบบ ไม่แสดงคำตอบรายข้อ รองรับ pagination, sorting, การค้นหาด้วยรหัสพนักงานหรือชื่อ–นามสกุล และตัวกรอง:

- ช่วงวันที่ส่ง
- บริษัท แผนก ตำแหน่ง และพื้นที่ปฏิบัติงาน
- เพศและช่วงอายุ
- อายุงาน: `<1 ปี`, `1–3 ปี`, `3–5 ปี`, `>5 ปี`
- กลุ่มที่เข้าเกณฑ์อย่างน้อยหนึ่งด้าน
- แบบประเมินและระดับผล
- Submitted หรือ Cancelled

หลายค่าในมิติเดียวใช้ OR และข้ามมิติใช้ AND

### 9.2 Dashboard

แสดงจำนวนผู้ส่ง จำนวนและร้อยละผู้เข้าเกณฑ์อย่างน้อยหนึ่งด้าน และผลแยกตามแบบ/ระดับ โดยใช้ตัวกรองเดียวกับตาราง เฉพาะ Submitted ที่ไม่ Cancelled

เมื่อขอบเขตหลังกรองมีน้อยกว่า 5 คน server ไม่ส่งค่าจริงและ UI แสดง “ข้อมูลไม่เพียงพอสำหรับแสดงสถิติ” กฎเดียวกันใช้กับ API และ export เชิงสถิติ

### 9.3 Export และ Reset

Admin export ข้อมูลเป็นไฟล์ Excel เท่านั้นตามตัวกรองปัจจุบัน ไม่รวมคำตอบรายข้อ ต้องยืนยันรหัสผ่านบัญชีผู้ใช้งานซ้ำก่อนดาวน์โหลด ไฟล์มีอายุสั้น ไม่ใช้ public URL มีคำเตือนข้อมูลอ่อนไหว และทุกครั้งบันทึก audit log

Admin Reset ต้องระบุเหตุผลและยืนยันการกระทำ ผลเดิมเปลี่ยนเป็น Cancelled โดยไม่ลบ

## 10. สถาปัตยกรรม

ใช้ monorepo แบบ Modular Monolith:

- `employee-web`: Vue
- `admin-web`: Vue
- `api`: Node.js modular application
- `shared-contracts`: types และ validation schemas
- PostgreSQL: system of record
- Object storage: export ชั่วคราว

Deploy ด้วย containers และถือ cloud provider เป็น infrastructure choice ที่ไม่เปลี่ยน application design สเปกนี้จึงกำหนดให้ใช้เฉพาะ interface/มาตรฐานที่ย้ายค่ายได้ และไม่อนุญาตให้ domain logic พึ่งบริการเฉพาะค่าย

โมดูล API คือ Employee Identity, Admin Identity, OnePlatform Adapter, Assessment Catalog, Assessment Session, Scoring, Results, Reporting, Export และ Audit/Retention กฎ domain โดยเฉพาะ Scoring ไม่อ้างอิง HTTP, Vue, PostgreSQL หรือ OnePlatform

## 11. Error Handling

- OnePlatform/token ผิดพลาด: ไม่สร้าง session หรือ Draft ให้เข้าสู่ระบบใหม่
- Autosave ล้มเหลว: คงคำตอบบน client แสดงว่ายังไม่บันทึกและ retry โดยไม่กล่าวว่าบันทึกแล้ว
- Session หมดอายุ: login ใหม่และกลับ Draft เดิม
- Submit ซ้ำ/timeout: idempotency คืนผลเดิมหากสำเร็จแล้ว
- Version หรือ scoring error: rollback transaction และคง Draft
- Unauthorized/forbidden: คืนสถานะมาตรฐานและ audit ตามความเหมาะสม
- Export error: ไม่ทิ้งไฟล์บางส่วน
- Production errors: แสดงข้อความภาษาคนและ correlation ID ไม่แสดง stack trace

Error contract ใช้ `code`, `message`, `fieldErrors`, `correlationId`

## 12. Security และ Privacy

- TLS ทุก environment ที่มีข้อมูลจริง และ encryption at rest สำหรับ database, backup, object storage
- ระบบทำการเข้ารหัส (Encrypt) ข้อมูลของพนักงานในระบบฟิลด์ ดังนี้: ชื่อ–นามสกุล, เพศ, อายุ, รหัสพนักงาน
- การแสดงผลจะต้องทำการ Masking ชื่อ-นามสกุล / รหัสพนักงาน ของพนักงานบนหน้าจอรายงาน เช่น “นายสมชาย ทำงานดี” >> “นายสมXXXX ทำXXXX” / INET9988776655 >> INET99XXXXXX55
- แยก Employee/Admin session และ cookie; ใช้ Secure, HttpOnly, SameSite
- CSRF/XSS/SQL injection defenses และ Content Security Policy
- ตรวจ authentication, authorization และ ownership ฝั่ง server ทุก request
- Admin เข้าสู่ระบบด้วยบัญชี OneID และ map สิทธิ์ Admin ในระบบ (2FA อยู่นอก Scope ระยะแรก)
- การ Export ข้อมูลต้องยืนยันรหัสผ่านของบัญชีผู้ใช้งานซ้ำก่อนดำเนินการ และส่งออกเป็น Excel เท่านั้น
- secrets อยู่ใน secret manager/environment injection
- least privilege สำหรับ database/storage และห้าม developer production access โดยปริยาย
- ห้ามเก็บคำตอบ `shareToken` รหัสผ่าน หรือข้อมูลสุขภาพใน logs/analytics
- บันทึก Audit log สำหรับการเข้าสู่ระบบ การดู/ส่งออกข้อมูล การคืนสิทธิ์ และกระบวนการทำงานทุกอย่าง (Event) ที่ผู้ดูแลระบบเข้าใช้งาน
- dependency และ container vulnerability scanning ก่อน deploy

## 13. Retention

เก็บ Submitted และ Cancelled ที่ระบุตัวได้ 1 ปีนับจากวันส่ง จากนั้นลบตัวระบุและ employee snapshot แล้วเก็บเฉพาะข้อมูลสถิติที่ไม่สามารถย้อนระบุตัวได้ หากมิติย่อยสร้างกลุ่มเล็ก ต้องตัดหรือรวมหมวดก่อนเก็บ

Audit log เก็บ 2 ปีและไม่เก็บคำตอบ รหัสผ่าน หรือ `shareToken` Retention job ต้อง idempotent มี audit และ backup/restore ต้องไม่ทำให้ข้อมูลหมดอายุกลับมาใช้งานปกติ

## 14. Non-functional Requirements

- พนักงาน 5,000 คน
- concurrent users สูงสุด 500 คน
- Availability 99.9%
- RTO 4 ชั่วโมง
- RPO 15 นาที
- WCAG 2.1 AA
- ภาษาไทยในเวอร์ชันแรก โครงสร้าง content รองรับ locale
- Employee Web รองรับ mobile/tablet/PC; Admin Web desktop-first และ responsive

## 15. Testing และ Acceptance

- Golden unit tests สูตรคะแนนและ boundary tests ทุก threshold
- ตรวจคำถาม 74 ข้อ รหัสไม่ซ้ำและถูกคิดคะแนนหนึ่งครั้ง
- State-machine, transaction, concurrency และ idempotency tests
- OnePlatform contract tests ด้วย mock
- Authorization/ownership tests
- PostgreSQL integration tests สำหรับ constraints, filter, suppression และ anonymization
- End-to-end tests ทั้งสองเว็บทุกขนาดอุปกรณ์เป้าหมาย
- Automated และ manual WCAG tests
- Load test 500 concurrent usersพร้อม safety margin
- Security tests และ vulnerability scanning
- Backup/restore drill พิสูจน์ RPO/RTO
- Clinical review และ legal/PDPA review ก่อน production

## 16. นอกขอบเขตเวอร์ชันแรก

- Campaign หรือการทำซ้ำรายปี
- Microservices
- Real-time risk notification และ emergency response workflow
- ภาษาอื่นนอกจากไทย
- การแสดงคำตอบรายข้อแก่ Admin
- การส่ง export ทางอีเมลอัตโนมัติ
- กราฟแนวโน้มผลส่วนบุคคลหลายช่วงเวลา

## 17. Production Gates

ก่อน production ต้องมีหลักฐานครบทุกข้อ:

1. ผู้เชี่ยวชาญอนุมัติคำถาม สูตร เกณฑ์ การแปลผล และคำแนะนำทุก version
2. เจ้าของระบบและผู้เชี่ยวชาญทบทวนการไม่แสดงช่องทางช่วยเหลือเมื่อพบความเสี่ยงฆ่าตัวตาย
3. ฝ่ายกฎหมาย/PDPA อนุมัติคำชี้แจง การเข้าถึงรายบุคคล export retention และฐานการประมวลผล
4. ผ่าน security, accessibility, load และ disaster-recovery acceptance tests
5. มี operational runbook, incident contacts และขั้นตอนจัดการบัญชี Admin
